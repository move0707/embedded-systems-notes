## 二、Linux 文件 IO：先把 fd 和数据搞清楚

### 1. “一切皆文件”在这节课是什么意思？

Linux 中许多设备能够通过**文件描述符**使用统一的 IO 接口，例如串口 `/dev/ttyUSB0`。但**不同设备的行为不一定相同**：普通文件读到末尾可以返回 `0`；终端/串口可能需要等待输入；网络套接字还涉及连接状态。不能理解成所有文件都具有完全相同的读写行为。

**文件路径 ≠ 文件描述符 ≠ 存储数据的缓冲区。**

| 名词 | 作用 | 示例 |
| :--- | :--- | :--- |
| 路径 | 用名字找到一个文件或设备 | `device.log`、`/dev/ttyUSB0` |
| `fd` | 一个**整数编号**，内核用它找到已打开的文件/设备 | `open()` 返回 `3`；`STDIN_FILENO` 是 `0` |
| 内核缓冲区 | 内核/驱动暂存输入或输出数据的位置，具体取决于设备 | 终端输入缓冲区 |
| 用户缓冲区 | 自己定义的 C 数组，调用 `read()` 后接收字节 | `char buffer[128]` |

**三个常用标准 fd**：`0` = 标准输入 `stdin`；`1` = 标准输出 `stdout`；`2` = 标准错误 `stderr`。在当前 VS Code 终端里，`fd=0` **通常**连接终端输入；它本身并不“等于键盘”，标准输入也能被重定向。

### 2. 四个核心系统调用

| 接口（常见头文件） | 做什么 | 返回值与注意点 |
| :--- | :--- | :--- |
| `open(path, flags, ...)`（`fcntl.h`） | 打开文件/设备，必要时创建 | 成功返回 `fd ≥ 0`；失败 `-1`；带 `O_CREAT` 时通常还需提供权限参数，如 `0644` |
| `read(fd, buf, count)`（`unistd.h`） | 尝试读取**最多** `count` 个字节到 `buf` | 返回 `>0`：实际读到的字节数；`0`：文件结束/相应设备的零字节返回；`-1`：错误（看 `errno`） |
| `write(fd, buf, count)`（`unistd.h`） | 尝试写入**最多** `count` 个字节 | 返回 `≥0`：实际写入字节数，**可能少于要求**；失败 `-1` |
| `close(fd)`（`unistd.h`） | 关闭当前 fd，释放对应引用/资源 | 成功 `0`；失败 `-1`；**不是给文件加锁** |

**两条关键链路（横向看）**：

`写文件：路径 → open() 得到 fd → write() → close()`  
`读文件：路径 → open() 得到 fd → read() 到 char 数组 → 处理字节 → close()`

```c
int fd = open("device.log", O_WRONLY | O_CREAT | O_APPEND, 0644);
if (fd == -1) { perror("open"); return 1; }

const char msg[] = "Device started\n";
ssize_t n = write(fd, msg, sizeof(msg) - 1);  // 返回实际写入字节数
if (n == -1) perror("write");
if (close(fd) == -1) perror("close");
```

| 常见标志 | 含义 | 容易弄错的地方 |
| :--- | :--- | :--- |
| `O_RDONLY` / `O_WRONLY` / `O_RDWR` | 只读 / 只写 / 读写 | `O_RDONLY` **不会自动创建文件** |
| `O_CREAT` | 不存在时创建文件 | 创建时要考虑权限参数；最终权限还受 `umask` 影响 |
| `O_APPEND` | 每次写之前定位到文件末尾 | 追加，不覆盖原有内容 |
| `O_TRUNC` | 满足相应打开条件时将已有普通文件截断为 0 字节 | 与 `O_APPEND` 含义完全不同 |
| `O_EXCL`（通常和 `O_CREAT` 组合） | 文件已存在时让这次创建失败 | **不是“禁止其他进程访问”或普通互斥锁** |

**为什么用 `ssize_t n`？** 因为 `read()`/`write()` 返回的是“字节数量**或** `-1`”，需要有符号类型。`sizeof(buffer) - 1` 是为后续可能添加的 `\0` 留位置；`read()` 读取的是原始字节，**不会自动添加字符串结束符**。

**遇到错误怎么判断？** 一般先检查返回值；返回 `-1` 时再看 `errno`，`perror("read")` 可以打印错误原因。不要只看有没有输出。复习代码还用了 `fwrite(buffer, 1, n, stdout)`：它是 C 标准库函数，按**字节数量**输出，不要求数据以 `\0` 结尾；与 Linux 的 `write(fd, ...)` 不是同一个接口。更多完整读写流程见 [file_io.c](./示例代码/file_io.c)。

## 三、阻塞 / 非阻塞 / poll：这一节的完整执行逻辑

### 1. 同一个 read，为什么一个等待、一个立即返回？

**区别不在 `read()` 这一行，而在 fd 的状态标志**。假设终端目前没有可读取的一整行输入：

| | 阻塞 fd（默认终端演示场景） | 非阻塞 fd（`O_NONBLOCK`） |
| :--- | :--- | :--- |
| 执行的调用 | `read(fd, buffer, 127)` | **同一个** `read(fd, buffer, 127)` |
| 当前没有数据 | **当前线程**在调用里等待 | 通常立即返回 `-1`，`errno = EAGAIN` 或 `EWOULDBLOCK` |
| 已经有数据 | 读取并返回 | 读取并返回 |
| 后续代码什么时候执行 | `read()` 返回之后 | 无数据时也能很快继续执行 |
| 是否卡住整个 Linux | **不会** | 不会 |

```c
int flags = fcntl(STDIN_FILENO, F_GETFL);          // 先读取原有文件状态标志
fcntl(STDIN_FILENO, F_SETFL, flags | O_NONBLOCK);  // 在保留原有标志的基础上启用非阻塞
ssize_t n = read(STDIN_FILENO, buffer, sizeof(buffer) - 1);
// 没有数据时，非阻塞 read 通常立即返回 -1，errno 为 EAGAIN/EWOULDBLOCK
fcntl(STDIN_FILENO, F_SETFL, flags);               // 示例结束后恢复原标志
```

**`fcntl()` 关键参数：** `F_GETFL` = 获取文件状态标志；`F_SETFL` = 设置可更改的文件状态标志；`O_NONBLOCK` = 非阻塞标志。`flags | O_NONBLOCK` 用按位或**增加标志**，不是清空其他标志。注意 `fcntl()` 自身也要检查是否返回 `-1`。

**不是“跳过 read”**：非阻塞模式依然真正调用 `read()`；只是当本次操作本来会等待时，立即以特定结果返回。

### 2. 你之前反复追问的重点：输入的数据究竟存在哪里？

在 VS Code 终端运行 `io_wait`，没有通过重定向替换标准输入时，通常是以下流程：

**键盘输入 `Hello` + 回车 → Linux 终端输入缓冲区（保存 `Hello\n`） → 内核使 fd=0 出现可读事件 → `poll()` 返回 → `read(0, buffer, ...)` 把字节复制到 C 数组 `buffer`。**

> [!important] 别混淆结构体和数据
> `pfd.fd = 0`：**仅存编号**，意思是“监听标准输入”。它**不存储字符**。  
> `pfd.events = POLLIN`：**想监听**“可读”这件事；不是说现在就可读。  
> `pfd.revents`：内核返回的**实际事件标志**，可能包含 `POLLIN`；它也**不存储字符**。  
> `buffer`：**只有真正调用 `read()` 后**才接收到输入字节。`poll()` 自己不搬运数据。

**为什么输入 `Hello` 还得按回车？** 当前终端一般工作在**规范模式（canonical mode）**，通常按回车形成一行后才使其可供 `read()` 读取。串口的输入行为可由串口设置决定，不能假设所有设备都要按回车。

### 3. poll 一次等待的全过程（即使没有 while）

```c
struct pollfd pfd = { .fd = STDIN_FILENO, .events = POLLIN };
int ret = poll(&pfd, 1, 5000);

if (ret > 0 && (pfd.revents & POLLIN)) {
    ssize_t n = read(STDIN_FILENO, buffer, sizeof(buffer) - 1);
    // 检查 n > 0、n == 0、n == -1 后再处理数据
} else if (ret == 0) {
    puts("等待超时");
} else if (ret == -1) {
    perror("poll");
} else {
    puts("发生了其他事件");
}
```

| 问题 | 直接答案 |
| :--- | :--- |
| `poll(&pfd, 1, 5000)` 的 3 个参数？ | `&pfd`：监听项目数组的地址；`1`：数组里 1 个 fd；`5000`：**最多等待 5000 ms** |
| `poll()` 返回什么？ | `>0`：有文件描述符报告了事件；`0`：超时；`-1`：出错，查看 `errno` |
| `revents & POLLIN` 是什么？ | **按位与检查**返回的事件里有没有可读事件；`ret > 0` **不等于一定是 `POLLIN`** |
| 没写循环为什么能等五秒？ | **调用 `poll()` 后，当前线程交给内核等待/唤醒**，不需要自己的代码反复执行 `read()`；事件到来可提前返回 |
| 有输入之后谁读取 `Hello`？ | **`read()`**，而不是 `poll()`，更不是 `pfd.fd` |
| 非阻塞之后为什么“又阻塞五秒”？ | **非阻塞 `read()`** 不等待；后面的 **`poll()` 是程序主动要求最多等五秒**，并不矛盾 |
| 要持续接收数据怎么办？ | **在程序外层写循环**，反复 `poll → 判断事件 → read → 处理`；当前课堂示例只执行一次 |
| 用非阻塞 while 不停 read 不行吗？ | 可以写，但没数据时会**忙轮询、浪费 CPU**；`poll()` 更合适 |

`poll()` 还可能报告 `POLLHUP`（挂断）、`POLLERR`（错误）、`POLLNVAL`（无效 fd）；即使报告可读，也仍须检查 `read()` 的返回值，不能保证一定读到了正数字节。

**补充函数 / 变量（本例用到了，但容易忽略）：**

| 写法 | 用途 |
| :--- | :--- |
| `argc`、`argv` | `argc` 是启动参数数量（包括程序名）；`argv[0]` 是程序名；`argv[1]` 在本例中是 `block`/`nonblock` |
| `strcmp(argv[1], "block") == 0` | 比较两个字符串内容；返回 `0` 表示**相等** |
| `STDIN_FILENO` | 标准输入的 fd，值是 `0`；不是“保存键盘内容的变量” |
| `fflush(stdout)` | 将 C 标准输出流里尚未输出的数据刷新出去，确保等待前提示能显示 |
| `errno` / `EAGAIN` / `EWOULDBLOCK` | 错误代码；非阻塞读取遇到“现在不能读”时的典型情况；两者在 Linux 上通常同值 |
| `perror("read")` | 根据当前 `errno` 打印可读错误信息 |
| `n > 0`、`n == 0`、`n == -1` | 依次表示读到字节、零字节返回、调用失败；不能一律当作字符串内容 |

### 4. 和 STM32 / 企业 Linux 项目对应起来

| STM32/FreeRTOS 里熟悉的概念 | Linux 中对应的理解 |
| :--- | :--- |
| `HAL_UART_Receive()` 等待接收完成或超时 | 阻塞 `read()` 在条件满足前可能等待（**不是同一个底层实现**） |
| UART 接收缓存与接收完成标志 | **内核缓冲区中的字节** 与 **`pollfd.revents` 的事件标志** 是不同的东西 |
| 周期检查通信状态 | `poll()` 可设超时，让上层有机会处理通信超时 |
| 一个任务负责通信、另一个任务负责监控 | 后续学习 `pthread`，由 Linux 调度多个线程 |

真实串口程序通常还需要配置 `termios`（波特率、数据位等）、正确处理半包/粘连、断线与超时、线程退出。**这些是后续课，不代表当前已掌握。**

---

**一句话自检**：`fd` 是编号；`pollfd` 保存**要监听什么与发生了什么事件**；用户输入先进内核管理的输入缓冲区；`poll()` 只等事件，真正把数据搬到 C 数组里的是 `read()`；阻塞/非阻塞说的是**当前线程调用 IO 时会不会等待**。
