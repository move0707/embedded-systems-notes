3、为什么要设计成双 MCU？为什么不让 ESP32-S3 一个芯片把联网和电机控制全做了？

```
不是因为 ESP 带不动，而是为了把不确定的网络任务和确定周期的实时控制隔离开
```

4、那既然双 MCU 之间需要通信，为什么你选择 UART，而不是 CAN？
```
这个项目 STM32 和 ESP32-S3 是点对点通信，主要传控制命令、状态和 OTA 数据，UART 已经够用，而且实现简单、调试方便、成本也低。CAN 更适合多节点总线场景，它有仲裁、错误检测这些机制，可靠性更强，但这里如果只有两个 MCU，用 CAN 会多引入收发器、终端电阻和协议复杂度，所以我把 UART 作为主链路，CAN 只保留作后续扩展。
```

5、那 CAN 比 UART 强在哪？
```
CAN 更适合多节点、抗干扰要求高的场景，有仲裁、错误检测和总线机制；UART 更简单，适合这个项目里两个 MCU 的点对点通信。
```

6、那你 UART 是怎么知道一帧数据从哪里开始、到哪里结束的？
```
UART 底层只能连续收到字节，所以我在应用层定义了帧头、命令、序号、长度、Payload 和 CRC16，接收端通过状态机逐字节解析，根据帧头确定开始、长度确定 Payload 大小，最后用 CRC16 校验完整性。
```

7、既然有帧头了，为什么还需要长度？
```
长度字段主要用于告诉接收端 Payload 有多少字节，方便确定一帧何时接收完整；数据内容是否出错主要由 CRC16 检查。
```

8、CRC16 是干什么的？为什么 UART 协议里还要加 CRC？
```
CRC16 用于检测 UART 帧在传输过程中是否发生误码。发送端根据帧内容计算 CRC 并附在帧尾，接收端收到后用相同算法重新计算，再和收到的 CRC 比较，不一致就认为这一帧有错误并丢弃。
```

9、如果 UART 一次 `read` 读到了两帧，或者只读到半帧，你怎么办？
```
UART 是字节流，一次 read 不一定正好对应一帧。接收端用状态机逐字节解析。
如果一次只收到半帧，就保留当前解析状态和已经收到的数据，等下一批字节继续收。
如果一次 `read` 收到了两帧，就解析完第一帧后继续处理剩下的字节，不能把后面的数据丢掉。
```

10、UART 是字节流，那你为什么不能认为一次 `read` 就是一帧？
`字节流：UART 只负责一个字节一个字节地往你这边送，它不知道哪几个字节属于同一条命令。`
`接收端用状态机记录当前解析到帧的哪个字段，逐字节接收，直到帧头、长度、Payload 和 CRC 都收完整，再交给上层处理。`
```
因为 UART 本质上是字节流，驱动每次 read 返回多少字节取决于当前缓冲区里有多少数据，不会自动按我的协议帧边界返回，所以要用状态机自己组帧。
```

11、Queue 和 Mutex 有什么区别？
```
Queue 主要用于任务之间传递消息和数据，比如通信任务收到电机控制命令后，通过队列交给电机控制任务处理。Mutex 主要用于保护共享资源，防止多个任务同时访问。比如 OTA 升级期间，UART 需要由 OTA 任务独占，避免与普通通信任务发生冲突。
```

12、那你为什么要通过 Queue 把 UART 收到的电机控制命令交给电机控制任务，而不是 UART 任务收到命令后直接控制电机？
```
Queue 就是让通信任务只负责收命令，电机任务自己去执行命令。这样 UART 收到数据后不用直接控制电机，两个任务分开，逻辑更清楚。
比如收到 `SET_RPM`，通信任务先把命令放进 Queue，电机控制任务再取出来更新目标转速，然后继续按 10 ms 周期跑测速、Ramp、PI 和 PWM。
```

13、你的 FreeRTOS 用了几个任务？用了哪些 Queue 和 Mutex？
```
STM32 侧主要有三个任务：电机控制、UART 通信和监督保护。通信任务和电机控制任务之间用了一个控制命令 Queue。ESP 侧主要处理 UART 通信、心跳、MQTT 和 OTA；STM32 OTA 时会暂停普通 UART 通信，由 OTA 任务独占串口，同时 ESP 自身 OTA 和 STM32 OTA 也需要互斥，避免两个升级同时进行。
```

14、如果连续来了两个 `SET_RPM`，第一个是 1000 RPM，第二个很快又改成 500 RPM，这时候电机会怎么跑？
```
如果先收到 `SET_RPM=1000`，随后又收到 `SET_RPM=500`，控制任务会按顺序处理这些命令，最终目标转速以最后处理到的 500 RPM 为准。Ramp 不需要先爬到 1000，再回到 500，而是从当前的 Ramp 值继续往新的 500 RPM 靠近。
```

15、那为什么要加 Ramp？为什么不能直接把 1000 RPM 目标送给 PI？
```
加 Ramp 是为了限制目标转速的变化速度，避免目标突然跳变导致 PI 误差过大，从而产生较大的电流和机械冲击。
```

16、那 Ramp 和 PI 到底是什么关系？为什么已经有 PI 了，还要再加 Ramp？
```
Ramp 输出的是“当前允许的目标转速”，PI 根据“Ramp 目标转速和实际转速的误差”去算控制输出，最后作用到 PWM 占空比。
```

17、PI 里面 P 和 I 分别是干什么的？
```
P 根据当前速度误差快速调节输出，I 累积历史误差，用来消除稳态偏差，最后 P 和 I 相加得到控制输出，再去调 PWM。
```

18、为什么你的项目用 PI，而不是完整的 PID？
```
我这里用 PI 没用完整 PID，主要是因为编码器离散测速有一定量化噪声，D 项可能放大抖动，而且 PI 配合 Ramp 已经能满足速度控制需求。
```

19、那你的 PI 多久计算一次？为什么是这个周期？
`周期太短，反馈更快，但编码器一个周期内计数太少，测速更容易抖；周期太长，测速更平滑，但控制响应会变慢。所以这里选 10 ms 做折中。`
```
PI 是在电机控制任务里面执行的，而电机控制任务每 10 ms 跑一次，所以 PI 也是每 10 ms 计算一次。
```

20、如果控制周期从 10 ms 改成 20 ms，积分公式里的 `Ts` 要不要改？
`每 10 ms，Ramp 只会更新一次“当前目标转速”；PI 再根据这个目标和实际转速的误差去调 PWM。至于电机实际速度能不能在这 10 ms 内追到这个 Ramp 目标，不保证。`

积分项：$I[k]=I[k-1]+K_i\times e[k]\times T_s$

```
需要，因为积分项和采样周期 Ts 有关。控制周期从 10 ms 变成 20 ms，Ts 也要从 0.01 改成 0.02，不然积分累计和实际时间不对应。

这一次的积分值 = 上一次已经积累的积分值 + 这一次新积累的一点误差。
```

21、如果电机反转，编码器算出来的 RPM 怎么知道要是负数？
```
编码器 A/B 相位关系决定计数方向，正转 CNT 增加，反转 CNT 减少，因此 10 ms 内的计数增量 ΔCNT 带有正负号，最后算出的 RPM 也就有正负。
```

22、为什么控制周期选 10 ms，而不是 1 ms 或 100 ms？
```
10 ms 是在控制响应速度和编码器测速稳定性之间做的折中。太短时编码器计数太少，测速噪声更明显；太长又会让控制响应变慢。
```

23、如果 `clear_fault` 返回成功，为什么系统还可能马上又进入 FAULT？
```
清故障只是清状态，不是消除故障源。如果超时、编码器异常或者过流条件还在，系统复查后会再次进入 FAULT。
```

27、！！！你这个 STM32 OTA，从远程发升级命令开始，到最后确认升级成功，完整流程是什么？
```
远程通过 MQTT 下发 STM32 OTA 命令，ESP 根据 URL 用 HTTPS 下载固件，并校验文件大小、SHA-256 和 CRC32。校验通过后 OTA 任务独占 UART，暂停普通通信，让 STM32 进入 Bootloader。然后按开始、数据、结束三个阶段把固件分包传给 Bootloader，Bootloader 写入 App 区并校验。最后启动新 App，ESP 等到新应用心跳和状态恢复后，才认为升级成功。
```

28、ESP 已经把固件下载成功了，能不能直接说“OTA 升级成功”？为什么？
```
不能。ESP 下载成功只能说明固件文件已经到 ESP。后面还要经过 Bootloader 接收、写入、镜像校验和新 App 启动。只有新应用正常启动并恢复心跳或状态反馈，我才认为整个 STM32 OTA 真正成功。
```

30、！！！OTA 升级过程中如果突然断电，系统应该怎么办？
```
OTA 过程中如果断电，重新上电后由 Bootloader 检查镜像有效标记和完整性校验。如果新 App 不完整，就不跳转到 App，而是保持在 Bootloader/恢复状态，等待重新升级。我的项目这里不能说成一定支持断点续传。
```

31、为什么 STM32 OTA 传固件时，要分成“开始包、数据包、结束包”三个阶段，而不是直接一股脑把 bin 文件发过去？
```
开始包用于让 Bootloader 进入升级状态，数据包负责分块传输固件，结束包表示传输完成并触发最终校验。这样比直接连续发送整个 bin 更容易做边界判断、应答和错误处理。
```

33、你这个项目里遇到过最难定位的问题是什么？你最后怎么解决的？
```
我项目里比较难定位的一次问题是 STM32 OTA 时 Bootloader 握手超时。最开始固件下载和校验都是正常的，但进入 UART 升级阶段后会超时，同时有普通协议解析异常。我把 OTA 拆成网络下载和串口传输两个阶段排查，最后发现普通 UART 任务和 OTA 任务会同时读取同一个串口，存在竞争，Bootloader 返回的数据可能被普通任务提前读走。后来我把 OTA 阶段的 UART ownership 统一起来，升级期间暂停普通通信，让 OTA 任务独占串口，并在失败和完成路径统一释放。修改后完成分包传输，新 App 能正常启动并恢复心跳。
```
